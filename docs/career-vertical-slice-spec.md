# 球员生涯首个垂直切片规格

## 1. 文档目的

本文定义球员生涯模块的首个“一周技术闭环”。它是开发、联调和验收的共同依据，目标是证明以下能力能够在同一个 Unity 客户端中可靠协作：

- 多本地档案与多条球员生涯；
- 新建球员、大学试训、周计划、行动与事件；
- 赛前准备、FakeMatch、比赛结算与周末推进；
- 原子保存、退出恢复、重复提交保护；
- UI Toolkit 下的键鼠与手柄完整操作。

本切片只覆盖大学第一赛季第一周，并以进入第二周 `Planning` 状态为终点。它验证的是技术闭环、模块边界和反馈完整性，不宣称已经验证六赛季节奏、长期成长平衡或最终玩法深度。

## 2. 前置条件与模块边界

### 2.1 开发基线

- 项目先通过独立变更升级并锁定 Unity `6000.3.20f1`。
- Editor 升级不得与本切片的功能开发、URP 迁移或 Input System 接入混为同一变更。
- 本切片的可见界面使用 UI Toolkit；输入基线接入官方 Input System 后，Career 与 Match 使用独立 Action Map。

### 2.2 责任边界

- Career 拥有本地档案、生涯状态、八项属性、成长、疲劳、心态、教练信任、周计划、事件和比赛后的长期后果。
- Match 只消费冻结的比赛上下文并返回比赛事实。FakeMatch 是 Match 网关的开发期实现，不得直接修改 Career 状态。
- Bootstrap 负责场景或页面流转、模块装配和比赛前后交接。
- Shared 只拥有稳定 ID、版本化比赛契约和跨模块值对象。
- Career UI 只能读取状态并提交应用命令，不得直接改写领域状态或存档文件。

### 2.3 Shared 契约门槛

仓库当前 `MatchContextV1` 已包含 `contractVersion`、`sessionId`、`seed`、双方阵容和 `contextHash`，当前 `MatchResultV1` 已包含比分及简化球员统计。正式实现 FakeMatch 前，双方必须通过独立的 Shared 变更确认本切片所需的版本字段、冻结参数、结果哈希和 fixture；Career 不得自行在内部复制或扩展跨模块 DTO。

契约升级至少满足：

- 比赛上下文和结果可独立序列化、校验并由双方读取；
- `sessionId`、契约版本和上下文哈希能够证明结果属于唯一的待处理比赛；
- 结果有稳定的 `resultHash`，重复结果与冲突结果能够区分；
- 比赛只报告事实，成长、疲劳、心态和信任后果仍由 Career 计算；
- 直接比赛与 FakeMatch 后续可以替换为同一网关和同一契约，不要求 Career 修改领域规则。

## 3. 范围

### 3.1 必须交付

- 创建、选择多个本地玩家档案；
- 每个本地档案创建、选择多条相互独立的球员生涯；
- 创建固定主攻位置的球员；
- 完成三段大学试训并生成初始状态；
- 安排并执行第一周两个自由行动槽和一个正式比赛槽；
- 执行四类常驻行动中的玩家选择；
- 完成一个固定社交事件样例；
- 选择一项赛前重点并完成 FakeMatch；
- 原子应用比赛后果和周末结算；
- 自动保存、退出、重新载入，并进入第二周 `Planning`；
- 完成七类开发期 UI、键鼠与手柄导航、开发调试面板；
- 通过成功、失败、重复提交和中断恢复验收。

### 3.2 最小内容集

- 一支大学球队：主角加 5 名固定队友；
- 一支大学对手：6 名固定球员；
- 第一周一场固定正式比赛，按当前原型能力为双方各选择 3 人；
- 三个固定试训环节；
- 四类常驻行动及其最小配置；
- 一个固定社交事件；
- 一组可版本控制的 FakeMatch 输入与结果 fixture。

球队、球员、训练、试训、事件和 fixture 均使用人工维护、不可复用的稳定业务 ID。显示名称不得作为存档归属、随机键或契约身份。

## 4. 核心状态与显示规则

### 4.1 球员基础信息

新建生涯只要求：

| 字段 | 规则 |
| --- | --- |
| 生涯名称 | 必填，用于生涯列表显示；不作为 `saveId` |
| 球员姓名 | 必填，用于界面与比赛阵容显示；不作为 `playerId` |
| 球衣号码 | `1–99` 的整数 |
| 位置 | 固定为主攻，不提供位置选择 |
| `careerSeed` | 创建时自动生成并持久化，不向普通玩家要求输入 |

本切片不提供外观、身高、体重、惯用手、出生地、背景故事或动作风格编辑。

### 4.2 八项属性

玩家可见属性为：扣球、发球、接发、防守、拦网、移动、弹跳、体能。

- UI 显示 `1–100` 的整数；
- 领域内部使用 `0–10000` 能力基点并单独保存成长经验，显示换算以规则版本为准；不得用显示文字或
  浮点累加作为权威状态；
- 训练与比赛事实增加对应成长经验，达到规则阈值后再改变显示属性；
- 进入比赛上下文时由明确、可测试的映射转换为 Shared 契约能力值；
- 本切片只要求一周后出现合理、可解释的成长反馈，不要求完成六赛季平衡。

### 4.3 潜力

- 玩家直接看到一个综合等级：`D / C / B / A / S`；
- 本切片中潜力只作为整体成长效率系数；
- 不设置八项隐藏上限、潜力区间、可信度或逐步揭示；
- 不创建没有调用方的空接口。未来扩展复杂潜力时通过规则版本和存档迁移加入。

### 4.4 心态、教练信任与疲劳

| 状态 | 显示 | 本切片来源与作用 |
| --- | --- | --- |
| 心态 | `0–100` 具体数值 | 由试训、社交事件和比赛结果改变；影响发挥稳定性或结算解释，不永久代替属性 |
| 教练信任 | `0–100` 具体数值 | 由试训、团队合练、赛前重点执行和比赛稳定性改变 |
| 疲劳 | `0–100` 具体数值 | 训练和比赛增加，休息降低；影响冻结到比赛上下文的有效能力 |

第一场比赛保证主角获得出场机会，不能因初始教练信任不足而阻断技术闭环。疲劳必须完整生效；伤病不进入本切片。

所有数值变化都必须返回“原因、旧值、变化量、新值”，供结算 UI 和自动化测试使用。数值越界时按规则钳制，并在结算摘要中展示实际生效量。

## 5. 端到端流程

标准成功路径为：

```text
选择或创建本地档案
  -> 选择或新建球员生涯
  -> 填写球员信息
  -> 完成三段大学试训
  -> 进入大学第一赛季第一周 Planning
  -> 安排两个自由行动槽，第三槽由比赛占用
  -> 确认整周计划
  -> 执行槽位 1
  -> 处理固定社交事件
  -> 执行槽位 2
  -> 选择赛前重点并创建 PendingMatch
  -> FakeMatch 返回固定比赛事实
  -> 原子结算比赛与周末并进入大学第一赛季第二周 Planning
  -> 从已提交快照显示比赛与周末总结
```

玩家在闭环中的每一个确认操作都必须有可理解的成功反馈。任何持久化失败不得让 UI 显示尚未成为权威存档的状态。

## 6. 本地档案与球员生涯

### 6.1 本地档案

- 首次启动且无档案时，显示创建本地档案入口；
- 玩家可以创建多个本地档案并在启动流程中选择一个；
- 每个档案具有稳定 `profileId` 和显示名；
- 本地档案不包含密码、注册、云同步或跨电脑识别；
- 档案索引损坏时，不得据此删除仍可验证的生涯文件。

### 6.2 多生涯

- 一个本地档案可以拥有多条球员生涯；
- 每条生涯具有独立 `saveId`、`careerSeed`、版本字段和 `lineageId/revision/snapshotHash` 版本令牌；
- 生涯列表至少显示生涯名称、球员姓名、阶段、赛季、周次和最近更新时间；
- 创建、保存或载入一条生涯不得改变同档案下其他生涯；
- 生涯索引是可重建摘要，完整生涯快照才是进度权威。

## 7. 三段大学试训

### 7.1 试训流程

试训依次完成三个固定环节，不能跳过或重复领取结果：

1. 进攻测试：形成扣球、发球和弹跳的主要初始样本；
2. 接发防守测试：形成接发、防守、拦网和移动的主要初始样本；
3. 综合对抗：形成体能、执行稳定性、初始心态和教练信任样本。

每个环节提供少量、明确的侧重点选择。选择影响对应初始结果，但不能直接选择“进攻型、均衡型或保障型”。试训输出由版本化配置、`careerSeed`、环节 ID、选择 ID 和稳定发生 ID 确定。

### 7.2 试训输出

三段全部完成后一次性确认入队状态：

- 八项初始属性与各自成长经验；
- 综合潜力等级；
- 初始心态、教练信任和疲劳；
- 主攻位置与球队归属；
- 大学第一赛季第一周日历。

退出并重新载入时，已完成环节不能重新抽取；未提交环节应回到原选择状态。相同生涯种子和相同选择必须得到相同结果。

## 8. 第一周计划与行动

### 8.1 槽位结构

第一周固定三个按顺序执行的行动槽：

| 槽位 | 内容 | 是否可调整 |
| --- | --- | --- |
| 1 | 玩家选择一项常驻行动 | 确认整周计划前可调整 |
| 2 | 玩家选择一项常驻行动 | 确认整周计划前可调整 |
| 3 | 第一周正式比赛 | 系统预留，玩家不可覆盖或移动 |

两个自由槽可以选择相同类别。确认前允许替换、清空和重新排序；确认后不得回退已完成行动。每个周计划、槽位行动、事件发生和执行操作都具有稳定 ID，删除后重新添加的行动必须产生新的发生 ID。

### 8.2 四类常驻行动

| 行动 | 玩家选择 | 最小真实后果 |
| --- | --- | --- |
| 专项训练 | 扣球、发球、接发、防守或拦网方向 | 对应能力少量直接经验、下一场对应比赛行为的成长加成、增加疲劳 |
| 力量训练 | 移动、弹跳或体能方向 | 对应能力少量直接经验、下一场对应负荷行为的成长加成、较高疲劳 |
| 团队合练 | 无额外强度选择 | 增加教练信任、少量综合经验和疲劳 |
| 休息 | 无额外强度选择 | 降低疲劳，使心态向稳定区间小幅恢复 |

本切片所有训练使用固定负荷，不提供轻度、标准、高强度等强度档位。重复选择同一训练允许执行，但具体收益和疲劳必须由同一版本化规则计算并在结算中解释。

## 9. 固定社交事件样例

### 9.1 触发条件

- 事件 ID 固定，第一周槽位 1 成功结算后触发一次；
- 事件不占用行动槽；
- 事件出现时周流程暂停，必须完成选择后才能执行槽位 2；
- 事件创建和玩家选择都必须保存，不能通过退出重新抽取。

### 9.2 事件内容

开发期样例为“训练后的队友邀约”，提供两个选择：

| 选择 | 主要方向 | 允许的有界随机后果 |
| --- | --- | --- |
| 参加球队聚餐 | 团队融入与放松 | 心态增加、教练信任小幅增加、疲劳可能小幅增加 |
| 留下与二传加练 | 排球配合与额外负荷 | 扣球或进攻配合经验增加、教练信任增加、心态小幅变化、疲劳增加 |

选择前显示收益和风险方向，选择后显示实际数值。具体区间由版本化事件配置给出；所有增减必须有明确上限，不允许普通社交随机直接大幅提高永久属性。

随机结果使用 `careerRandomAlgorithmVersion = 1` 的稳定键派生，键至少区分 `careerSeed`、事件流、赛季、周次、事件 ID、`occurrenceId` 和 `drawIndex`。相同存档状态和选择必须得到相同结果，插入其他系统的随机调用不得改变本事件。

## 10. 赛前重点与 FakeMatch

### 10.1 三项赛前重点

比赛槽开始前，玩家必须选择且只能选择一项：

| 重点 | Career 侧最小效果 |
| --- | --- |
| 优先进攻 | 提高扣球、发球等进攻事实带来的成长权重，并在赛后解释执行结果 |
| 保障一传 | 提高接发、防守事实带来的成长权重，并在赛后解释执行结果 |
| 控制体能 | 降低本场工作负荷转化为长期疲劳的幅度，但不伪造比赛统计 |

赛前重点、有效能力、阵容、版本和比赛种子必须在创建 `PendingMatch` 时冻结。返回赛前页面可以更改尚未确认的重点；`PendingMatch` 成功保存后不得在比赛运行期间修改。

### 10.2 FakeMatch 行为

- FakeMatch 接收与真实比赛相同的冻结上下文；
- 首个样例返回版本控制中的固定比赛事实，不访问 Career 内部状态；
- 结果至少能驱动比分展示、主角比赛记录、成长、疲劳、心态和信任结算；
- fixture 必须带有稳定来源和预期哈希，测试不得手工篡改结果来绕过校验；
- UI 明确标注这是开发阶段的模拟比赛；
- 以后替换为真实 Match 时，Career 的周流程和结算用例不应改变。

FakeMatch 的固定结果不用于证明比赛平衡或 AI 合理性。赛前重点可以改变 Career 对相同比赛事实的后果计算，但不得反向改写结果事实。

## 11. 比赛与周末原子结算

### 11.1 比赛结算顺序

Career 收到结果后必须按以下业务顺序处理：

1. 重新计算并验证结果哈希；
2. 按 `sessionId` 查询既有 `SettlementReceipt`；
3. 已存在相同上下文与结果哈希时，返回原结算摘要，不重复应用；
4. 同一 `sessionId` 对应不同哈希时报告冲突，不覆盖现有状态；
5. 首次结算时校验 `PendingMatch`、上下文、赛程和预期修订；
6. 生成完整下一版快照，并通过单写者保存队列一次提交。

同一修订必须同时包含：原始比赛结果、哈希、所有比赛及周末 Career 后果、比赛历史、
`SettlementReceipt`、已清除的 `PendingMatch`、已完成的第一周和第二周 `Planning`。UI 只能在原子
替换成功后显示结算完成。

### 11.2 周末汇总与确认

第一周最后一场比赛没有后续槽位，因此首次比赛结算命令必须同时完成周末结算：

- 汇总两次自由行动、社交事件和比赛造成的属性经验变化；
- 应用并展示疲劳、心态和教练信任的最终变化；
- 记录第一场比赛历史与累计统计；
- 完成第一周并创建第二周的空周计划容器；
- 第二周开始时保持 `Planning`，不预先生成具体行动或比赛占用；第二周赛程内容不属于本切片；
- 周次递增和第二周 `Planning` 的建立与比赛结算属于同一次原子提交。

原子替换成功后，界面从新快照和 `SettlementReceipt` 显示比赛与周末总结。玩家确认只关闭汇总并回到
已经存在的第二周主页，不触发第二次领域结算或空 revision；重启后可从历史/通知再次查看相同摘要。

## 12. 七类 UI 页面

本切片严格限制为以下七类页面或页面组：

1. **本地档案选择与创建**：列出档案、创建档案、选择当前档案，并显示载入或恢复错误。
2. **球员生涯列表与新建**：列出当前档案下的所有生涯，创建或载入一条生涯。
3. **球员信息及大学试训**：填写必要字段、依次完成三段试训、查看并确认初始结果。
4. **生涯主页与周行动安排**：显示球员摘要、八项属性、潜力、心态、信任、疲劳、周次和三个槽位；完成规划、确认及安全状态下的立即保存。
5. **赛前重点选择**：展示对手、阵容摘要、三项重点和确认状态；有 `PendingMatch` 时作为重赛入口。
6. **比赛总结**：展示 FakeMatch 比分、主角事实统计、赛前重点执行解释和 Career 后果摘要。
7. **周末结算与通知弹窗**：汇总全周变化、显示事件与保存结果，并进入第二周。

UI 使用统一的开发期视觉样式，不要求正式美术、角色外观、动画演出、音效或复杂转场。页面必须清楚区分“尚未确认”“正在保存”“保存完成”“无法保存”和“只读/恢复中”等状态。

## 13. 输入、显示与本地化

### 13.1 键鼠与手柄

七类页面必须同时支持：

- 鼠标点击、滚轮、键盘方向导航、确认、取消和返回；
- 常见 XInput 手柄的方向导航、确认、取消、返回和页面切换；
- 始终可见且唯一的当前焦点；
- 弹窗打开后焦点留在弹窗内，关闭后返回原触发控件；
- 列表与滚动区域中的焦点项自动滚入可视区域；
- 返回操作不能绕过保存、计划确认或比赛待处理状态。

本切片不包含按键重绑定界面。

### 13.2 窗口与分辨率

- 最低可用分辨率为 `1280×720`；
- 主要验收分辨率为 `1920×1080`；
- 支持窗口化与无边框全屏；
- 调整窗口后关键状态、按钮和错误信息不得被裁切或永久移出视口；
- 超宽屏、4K 专项布局和多显示器不作为门槛。

### 13.3 简体中文

- 本切片只提供简体中文玩家文案；
- 显示文案集中到本地化资源或统一文案表；
- Domain、存档、契约、随机键和测试只使用稳定 ID、枚举和数值，不保存中文显示文本作为业务依据；

## 14. 开发调试面板

调试面板只在 Unity Editor 或 Development Build 中可见，至少能够查看：

- `profileId`、`saveId`、`lineageId`、`revision`、`snapshotHash` 和 `careerSeed`；
- 当前适用的 `schemaVersion`、`contentVersion`、`rulesetVersion`、`contractVersion` 和随机算法版本，
  以及 FakeMatch fixture ID/版本；尚未实现的比赛模拟版本显示 `N/A`，不写入存档占位；
- 当前阶段、赛季、周次和持久化周状态；
- 三个槽位、稳定行动 ID、事件发生 ID 和操作 ID；
- `PendingMatch`、上下文哈希、结果哈希与 `SettlementReceipt`；
- FakeMatch fixture 标识；
- 最近一次保存、载入、结算或恢复的结果与错误码。

调试操作至少包括：立即保存、重新载入、选择允许的 FakeMatch fixture、模拟下一次保存失败，以及导出脱敏诊断信息。调试操作不得出现在正式非开发构建，也不得绕过领域校验直接改写生产存档。

## 15. 保存与恢复体验

### 15.1 自动保存点

至少在以下权威变化后自动保存：

- 本地档案或生涯创建完成；
- 每段试训结果确认；
- 整周计划确认；
- 每个行动槽结算；
- 社交事件创建与选择结算；
- 进入比赛前创建 `PendingMatch`；
- 比赛结果、周末后果与第二周建立一次原子结算。

玩家只可以在安全的 `Planning` 状态选择“立即保存”。比赛、行动或结算进行中不提供任意手动快照和多手动存档位。

### 15.2 玩家可见恢复规则

- 主存档损坏时保留并隔离原件，验证唯一上一修订备份后提示玩家确认恢复；
- 备份无效时拒绝覆盖和静默新建，提供可导出的诊断信息；
- 比赛中退出或崩溃后回到赛前重点页，复用原 `sessionId`、上下文和比赛种子从开头重赛；
- 本切片不从局分、轮转、球或角色姿态中途继续；
- 保存提交前失败时继续以旧修订为权威，提交成功后失败时通过回执识别已完成操作；
- 陈旧修订提交被拒绝后，重新载入权威状态并向玩家解释冲突，不静默覆盖。

## 16. 验收标准

### 16.1 成功路径

以下条件全部满足，才算完成标准闭环：

- 可以创建至少两个本地档案，并在每个档案下创建至少两条互不影响的生涯；
- 球员姓名、球衣号码和生涯名称校验正确，位置始终为主攻；
- 三段试训顺序完成，并生成八项属性、潜力、心态、信任和疲劳；
- 第一周只能安排两个自由行动，第三槽始终为比赛；
- 四类常驻行动均能产生可见、可解释且可保存的最小真实后果；
- 槽位 1 后只触发一次固定社交事件，两项选择均可完成并产生有界结果；
- 三项赛前重点均可选择、冻结，并在赛后说明其 Career 影响；
- FakeMatch 结果通过契约和哈希校验，比赛事实与 Career 后果边界清晰；
- 比赛结算、回执、清除 `PendingMatch` 和新修订一次原子提交；
- 周末总结展示八项属性或经验、疲劳、心态、信任和比赛记录变化；
- 流程最终进入大学第一赛季第二周 `Planning`，并有可恢复的空周计划容器；
- 退出应用再载入后，选项、随机结果、比赛历史、数值和周状态完全一致；
- `1280×720` 与 `1920×1080` 下均可用键鼠和手柄完成全流程。

### 16.2 失败路径

必须验证并给出明确 UI 反馈：

- 空姓名、空生涯名称、非法球衣号码不能创建生涯；
- 未完成三段试训不能进入第一周；
- 未填满两个自由槽、试图覆盖比赛槽或计划状态已过期时不能确认；
- 未处理社交事件不能继续槽位 2；
- 未选择赛前重点不能创建 `PendingMatch`；
- 不支持的契约版本、错误上下文哈希、未知球员 ID 或不属于待处理比赛的结果不能结算；
- 同一 `sessionId` 对应不同结果哈希时报告 `SessionResultConflict`，不改变存档；
- `expectedVersionToken` 不匹配时报告 `VersionConflict`，不覆盖权威快照；
- 临时文件写入、校验、刷新或原子替换失败时，不发布部分新状态；
- 主存档与备份均损坏时拒绝进入可写生涯，不静默清空进度。

### 16.3 恢复与幂等

在关键提交的“成功前”和“成功后”分别注入中断，至少覆盖：

- 三段试训中的任一段；
- 整周计划确认；
- 两个自由行动槽；
- 社交事件出现与选择；
- 创建 `PendingMatch`；
- FakeMatch 结果、周末结算和第二周建立的联合提交。

恢复后必须证明：

- 已成功提交的后果不丢失，未提交的后果不提前出现；
- 同一行动、事件、比赛或周末操作不会重复应用；
- 同一随机键重新计算得到相同结果；
- 相同比赛结果重复提交返回原 `SettlementReceipt` 摘要；
- 比赛待处理状态只回到赛前重赛，不声称支持比赛中途续玩；
- 第一周完成与第二周建立不会出现一半完成的状态。

### 16.4 验收证据

- Career 与 Shared 新增规则具有 EditMode 自动化测试，整套 EditMode 全绿；
- UI 的键鼠、手柄、弹窗焦点、滚动和返回路径具有 PlayMode 覆盖；
- 保存测试覆盖往返、损坏、备份恢复、完整版本令牌冲突（含同 revision、不同 lineage/hash）与原子
  替换失败；
- FakeMatch 测试覆盖契约校验、重复结果幂等和不同哈希冲突；
- Windows x64 Development Build 能完成完整闭环并导出脱敏诊断；
- 两名开发者分别在实体 Windows 机器上完成一次闭环试玩；
- 对应变更记录列出测试命令、结果文件和已知限制。任一硬门槛失败时，不把本切片标记为完成。
