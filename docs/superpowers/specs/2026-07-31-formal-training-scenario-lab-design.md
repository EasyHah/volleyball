# 正式训练情景实验室设计

- 日期：2026-07-31
- 状态：已确认
- 范围：Match / Formal 6v6 / 独立训练场景 / 开发者 UI / 诊断
- 首个验收主题：V4 统一首次触网续球

## 1. 目标

新增一个独立的可视化训练情景实验室。开发者可以在比赛启动前编辑一个受约束的合法回合起点，
校验通过后使用现有正式 6v6 的球体、12 名球员、AI、触球规则、物理碰撞和裁判链路运行。

实验室首先解决现有 `FormalMatchScenarioDefinitionV4` 只能表达开球输入、无法冻结第二或第三触球后
状态的问题，并以五类触网续球情景完成第一个功能闭环。它同时为后续玩家训练模式和 AI 决策样例
采集提供稳定基础，但本里程碑不实现玩家控制、大模型教师或本地深度学习模型。

## 2. 已确认决策

1. 使用独立训练实验室场景，不把编辑界面叠加到正式比赛场景。
2. 基础物理、球员执行、AI、V3 触球规则和裁判必须复用现有正式实现，不复制简化版本。
3. UI 采用一体化指挥台：左侧情景库、中间 3D 球场、右侧属性与校验、底部运行时间线。
4. 第一版支持受约束自由编辑：球和 12 名球员、球运动、语义化回合起点、战术及 Context 的
   `matchSeed`。
5. 用户只能选择语义化合法起点；底层触球数、窗口、权威和 Block 状态由规则工厂派生，只读展示。
6. 第一版只运行全 AI；不允许玩家接管球员。
7. 开发者模式首期只支持键盘和鼠标编辑；玩家权限层保留接口，手柄编辑延期。
8. 运行前必须校验并冻结不可变情景；运行后编辑器完全锁定。
9. 支持暂停、固定物理步单步、只读时间线、重置、同 `matchSeed` 重跑与运行对比。
10. 不支持从任意时间点恢复完整 Unity 物理世界后继续运行；时间线跳转只用于查看。
11. 旧 `FormalMatchScenarioDefinitionV4`、既有开球资源、内容哈希和 V4 公共合同保持不变。
12. 第一版导出规范化决策快照、合法候选和当前选择，为后续 AI 里程碑提供输入，但不调用模型。

## 3. 当前事实与缺口

`FormalMatchScenarioDefinitionV4` 明确不包含中回合球状态、强制触球或预期结果。当前启动链只能在
Director 初始化前注入 Context、轮转、战术、AI 和发球轨迹参数，因此能够稳定表达发球触网，却
不能合法表达：

- 第二触球后球擦网留在本方；
- 第三触球后球擦网留在本方或越网；
- Block 后球再次触网；
- 同一飞行段多次物理触网。

依赖长整局自然产生这些事件既慢又不稳定。测试中途直接移动球、提交触球或写比分又会绕过正式
物理和规则权威，不能作为验收证据。

## 4. 权威边界

### 4.1 编辑阶段

训练 UI 只编辑 `TrainingScenarioDraftV1`。草稿不属于比赛权威状态，不能直接引用或修改运行中的
Director 私有字段。

校验成功后，草稿生成不可变、版本化、可规范序列化和可哈希的 `TrainingScenarioV1`。该值只允许
在训练场景首个物理帧前消费一次。

### 4.2 运行阶段

训练场景使用与正式 6v6 相同的组合根创建：

- `SimulatedBall` 与现有球体积分、碰撞和网体；
- Context 中完整的 12 名球员及现有执行组件；
- 现有 AI、战术规划、动作窗口和可达性判断；
- V3 触球规则及 accepted-contact 权威；
- 现有 ground/out/net、轮转、计分和回合裁判。

运行开始后禁止：

- 直接提交或伪造 accepted contact；
- 强制动作成功或失败；
- 设置预期裁判结果；
- 修改比分；
- 移动球或球员；
- 绕过合法性、物理碰撞、可达性或裁判链路。

暂停和单步只控制正式模拟的推进，不授予编辑权限。

### 4.3 观察阶段

诊断、时间线、运行对比和自动测试只订阅权威事件。观察器不能发布 movement/contact command，
不能读取对手隐藏最终路线或未来执行样本，也不能改变正式选择。

## 5. 情景模型

### 5.1 `TrainingScenarioDraftV1`

仅供 UI 使用的可变草稿，包含：

- 完整 `MatchContextV4`；
- 情景 ID、显示名和来源；
- 双方战术与 AI 配置；
- 12 名球员的可编辑初始空间状态；
- 球的初始位置、线速度和角速度；
- 一个语义化回合起点；
- 开发者/玩家权限配置。

草稿可以无效，以便 UI 在编辑过程中逐项显示错误；它不能启动比赛或计算正式 provenance。
运行时唯一随机源仍是 `MatchContextV4.Seed`。UI 中的 `matchSeed` 字段编辑草稿 Context 的 seed，
不得新增第二个场景随机源。

### 5.2 语义化回合起点

首版只提供系统明确支持的起点类别，例如：

- `ServeFlight`
- `AfterFirstCountedContact`
- `AfterSecondCountedContact`
- `AfterThirdCountedContact`
- `AfterAcceptedBlock`

用户选择起点类别和来源队伍后，由现有规则层旁的专用初始化工厂派生：

- 当前触球方和已计数触球数；
- 合法下一动作集合；
- 必须失效或不存在的旧窗口；
- 普通续球与 post-block continuation 的排他状态；
- 回合是否处于 active 状态。

开发者可以查看这些派生值，但不能逐字段覆盖。若新的训练需求无法由现有类别表达，应新增一个
带规则测试的语义类别，而不是开放任意底层状态编辑。

### 5.3 `TrainingScenarioV1`

校验后的不可变运行输入。它保存草稿的规范值和派生后的规则起点，并计算内容哈希。所有浮点值
必须有限，规范编码使用固定字段顺序和 invariant culture。情景资源的 supplied hash 与重算结果
不一致时拒绝加载。

既有 Replay V4 schema 不增加字段。训练运行仍写入已有 scenario provenance：

- `scenarioId` 使用 `training-v1/` 命名空间；
- `contentHash` 使用完整 `TrainingScenarioV1` 内容哈希；
- provenance envelope 保持既有格式版本。

训练情景自己的格式版本属于哈希载荷，不改变 Shared Replay V4 的规范 bytes 或字段集合。
`TrainingScenarioV1` 是 Match-owned 的训练基础设施值，不进入 Shared 或 Career 公共合同。

### 5.4 空间状态

每名球员按稳定 `PlayerId` 对应 Context 中的唯一球员，并保存位置、朝向及初始化所需的现有动作
姿态。球保存位置、线速度和角速度。情景值不得保存运行中的 Unity 对象引用。

首版不保存任意物理检查点、碰撞器内部缓存、异步 continuation、已排队回调或历史事件。所有允许
恢复的状态必须能由语义化起点和现有初始化工厂完整、确定性地建立。

## 6. 严格校验

一个情景只有在以下条件全部满足时才可运行：

1. Context、配置、战术、AI、`matchSeed` 和情景标识完整，且不存在第二个运行时随机源。
2. 球员集合与 Context 的 12 人完全一致，按稳定 ID 对应，无缺失、重复或替换。
3. 球员和球的数值有限，位置位于情景编辑允许区域。
4. 球员碰撞体不存在非法初始穿插，球不从非法实体内部启动。
5. 球状态与语义化回合起点方向、来源队伍和允许区域相容。
6. 触球数、普通续球、第三触球上限及 post-block 排他状态由规则工厂成功派生。
7. 第三触球后不会预置本方第四次触球窗口。
8. post-block 起点不会同时预置普通触网续球权威。
9. 输入中不存在比分结果、强制触球结果、预定裁判结论或“下一动作必须成功”。
10. 格式版本受支持且 supplied content hash 匹配。

校验器返回稳定的问题代码、对象 ID 和属性路径。UI 在球场和属性面板中同时定位错误；任何 error
都禁用运行。warning 可以提示边界或低质量起点，但不得自动修正后静默启动。

## 7. 场景与界面

### 7.1 独立场景

新增独立训练实验室场景。它可以复用正式 6v6 的场地与组合构建器，但有自己的启动入口、编辑
相机、UI 根和训练生命周期控制器。正式比赛场景不加载训练编辑器。

训练场景是否进入发行构建由显式构建配置控制。首期至少进入 Windows Development Build 的验收
构建；普通发行构建默认不暴露开发者入口。未来玩家训练模式启用时再明确发行入口。

### 7.2 一体化指挥台

- 左侧：项目内置标准情景、当前会话草稿、新建、复制及重置。
- 中间：3D 球场，选择并拖放球或球员，显示轨迹预览和错误定位。
- 右侧：所选对象属性、语义化起点、派生规则状态、战术、`matchSeed` 和校验结果。
- 底部：校验、运行、暂停、固定步单步、重置、时间线和关键事件摘要。

编辑阶段使用键鼠。拖放必须经过球场约束与即时校验；属性面板是同一草稿的另一视图，不维护
第二份状态。

首版不实现运行时情景文件的导入、跨会话保存或任意路径写入。可回归的标准情景由项目资源提供；
当前会话草稿只保存在内存中。持久化用户情景必须在后续任务中单独设计路径、迁移和文件恢复。
决策快照只允许在 Unity Editor 中导出到已忽略的 `TestResults/TrainingLab/DecisionSnapshots/`；
Windows Development Player 只显示快照摘要，不写出数据集文件。

### 7.3 权限层

UI 和情景元数据从首版区分：

- `Developer`：允许受约束的完整编辑、诊断和导出；
- `Player`：未来只允许选择训练项目、难度和显式开放参数。

首版只交付 `Developer`。权限层不能改变运行器、规则或物理，只决定编辑器暴露哪些草稿命令。

## 8. 生命周期与错误处理

状态机为：

`Editing -> Validating -> Ready -> Running <-> Paused -> Completed`

- 校验失败返回 `Editing` 并保留草稿。
- `Ready` 生成并显示情景 hash 与权限摘要。
- `Running` 和 `Paused` 锁定编辑器。
- `Paused` 只允许固定物理步推进、观察和继续。
- `Completed` 显示结果、触球序列、触网/续球/窗口证据及裁判事件。
- 返回编辑必须丢弃运行实例并从草稿重新构建；不能把运行中的世界反写成草稿。

运行异常时立即冻结本次运行，保留情景 hash、`matchSeed`、最后规则事件和诊断快照。系统不得自动
修正状态后继续。用户可以导出诊断、同输入重跑或返回编辑。

暂停与单步由训练生命周期控制器驱动现有固定步模拟入口；wall-clock、界面帧率和日志耗时不得
改变规则决策或步进次数。

## 9. 时间线、重跑与确定性

时间线记录现有公开权威事件及本任务需要的只读诊断证据。跳转到历史节点只用于查看已记录状态；
从该节点继续模拟不在首版范围内。

确定性门禁分为：

- 同平台、同构建、同情景 hash、同 `MatchContextV4.Seed`：规则结果、accepted-contact 序列、
  续球证据和决策
  输出必须严格一致；
- macOS 与 Windows：触球上限、合法性、唯一判分和候选排序等语义不变量必须一致；物理轨迹采样
  和时间允许有界浮点差异。

任何同平台双跑不一致都视为缺陷，不能用测试容差掩盖。

## 10. 决策快照预留

第一版允许在计划触发点生成 Match-owned 的规范化 `DecisionSnapshotV1`，包含：

- 决策时可见、版本化的比赛状态特征；
- 现有系统生成并通过合法性过滤的候选；
- 现有选择及其公开评分/原因；
- 情景 hash、规则/特征编码版本和来源 sequence。

快照不得包含对手隐藏最终路线、未来执行样本、最终物理结果或无法在决策时观察的事实。快照只供
查看和导出，不影响正式选择。它是本地开发数据格式，不进入 Shared Replay、Result 或 Career
合同；后续里程碑若需要兼容演进，必须独立版本化。

后续独立里程碑按以下顺序推进：

1. Editor-only MenShen 教师为合法候选提出排序；
2. 人工接受、纠正并标注其他候选的问题原因；
3. 以分歧度和低置信度建立主动学习队列；
4. 校准期逐条审核，扩量期允许 teacher-only 预标注和持续抽检；
5. 黄金集只包含人工确认样例；
6. 本地学生模型以固定特征和模型版本影子推理；
7. 是否成为权威排序器必须另开高风险任务决定。

本里程碑不调用大模型、不保存教师标签、不训练或加载本地模型。

## 11. 首批触网情景

首版必须提供：

1. `SecondTouchNetOwnSide`：第二触球后擦网留本方，只有真实几何第三触球才能续球。
2. `ThirdTouchNetOwnSide`：第三触球后擦网留本方，不产生第四触球，由唯一裁判结果结束。
3. `ThirdTouchNetCross`：第三触球后擦网越网，对方只在真实 crossing 后获得防守机会。
4. `PostBlockNet`：通用触网分派为零，只走既有 post-block continuation。
5. `NetDeflectionSingleDispatch`：同一 flight segment 多次触网最多一次 replan/window publication。

每个关键情景固定 key 双跑，比较结果、accepted-contact 序列和 continuation evidence；至少包含一个
不可达变体，证明不会自动救球或伪造触球。

## 12. 实施分段

### 阶段 A：合同与校验

- 情景草稿、不可变定义、语义化起点、规范 hash；
- 规则初始化工厂；
- 合法/非法组合 focused EditMode。

### 阶段 B：无 UI 正式运行器

- 首帧前一次性消费；
- 正式 6v6 组合根复用；
- 无 UI 的 fixed-seed PlayMode 与确定性双跑。

### 阶段 C：独立场景与开发者 UI

- 一体化指挥台；
- 键鼠编辑、轨迹预览、校验定位；
- 运行锁定、暂停、固定步单步、重置和时间线。

### 阶段 D：首批情景与收口

- 五类触网情景及不可达变体；
- 决策快照查看/导出；
- 受影响回归、Windows Development Build 和实机验收。

## 13. 验收与验证

实现冻结后至少完成：

1. 情景 codec/hash/validator/semantic factory focused EditMode。
2. 受影响 Match EditMode。
3. 五类触网指定 PlayMode 双跑及不可达变体。
4. 既有正式场景资源、Replay provenance 和 defensive continuation 回归。
5. 一条正式 6v6 整局 smoke。
6. 人工检查拖放、属性同步、错误定位、运行锁定、暂停、单步、重置和同 `matchSeed` 重跑。
7. Windows x64 Development Build。
8. Windows 键鼠实机验收训练实验室和正式比赛入口。
9. Repository validation、`git diff --check`、构建列表和最终 diff 检查。
10. 删除 Unity 生成的 `Assets/InitTestScene*.unity` 及对应 `.meta` 临时文件。
11. 一次独立全面复核；高优先级问题集中修复后只做一次针对性复审。

自动检查通过后状态为“待人工验收”；必要的 Windows 实际操作确认后才能标记“完成”。

## 14. 兼容、回滚与所有权

- 不修改 `MatchContextV4`、`MatchResultV4`、`MatchReplayV4` 或 Career 存档。
- 不改变旧正式情景的构造、资源、内容 hash 或开球行为。
- 训练模型、场景、UI 和诊断由 Match 所有；不得引入 Match/Shared → Career 依赖。
- 若训练入口失败，可从构建列表移除独立场景并回滚训练模型/运行器，不影响正式比赛。
- 若只读诊断导致行为差异，必须移除或修复观察器；不能接受“打开诊断会改变比赛”。

## 15. 非目标

- 玩家接管球员、正式玩家训练菜单或手柄编辑导航；
- 任意底层规则字段编辑；
- 从任意物理检查点倒放后继续；
- 复制或简化正式物理、AI、规则、触球或裁判；
- 大模型教师调用、标注数据集管理、本地模型训练或推理；
- 让任何模型直接设置球速、移动球员、绕过合法性或裁判；
- 修改 V4 公共合同、Career 生命周期、存档或结算；
- 多局制、换人、自由人替换或其他 V5 玩法。
